# Phase 23 Workshop (embedded-DCC gate scene)

Generated by `inf_editor_core::samples::phase23_workshop_scene` -- the P23.6 gate
scene, and the smallest sample in the tree on purpose. Every other phase gate ships a
level whose *content* is the claim; this phase's claim is about a **pipeline** (model,
unwrap, save, live-update, undo, deterministic replay), so the level's job is only to
reference a mesh and keep simulating while that mesh is edited underneath it.

- `Phase23Workshop.inf_lvl` -- a sun, a static floor, and one dynamic prop whose
`MeshRef.asset` names the mesh below. **Visibly coupled, physically independent**:
the prop draws the asset the gate rewrites, and its collider is authored, so a mesh
edit cannot reach the simulation. That pair is the whole shape of the P23.1
asset-scoped ruling.
- `Prop.inf_mesh` -- the **import baseline**: a 2 m cube written through the DCC's own
`to_mesh_asset`. It is committed rather than generated at test time because the gate's
undo arm compares a fully-undone journal against it *byte for byte*, and a hand-built
asset would differ in its corner interning order alone (part of the format, per the
P23.3 law).

## The gate (`runtime/inf-player/tests/phase23_gate.rs`)

Nine arms, all driven through the product op path rather than hand-built meshes:
(a) model a prop -- extrude, then loop cut, then bevel (that order: an edge ring is only
defined across quads, so the cut needs the extrusion walls and a bevel first would replace
the very edges the ring walks). The bevel takes TWO OPPOSITE rim edges and not all four:
bevels that MEET at a corner each offset it into their far face, on a right angle both land
at one position, and the reader's exact weld fuses them into a non-manifold edge -- so
`Op::BevelEdges` refuses that, and the gate asserts both the refusal and the pair that
works. Then the journal is replayed twice, bit-identically;
(b) seams + unwrap: every corner inside the unit square, ZERO folds, and the convergence
field at machine epsilon on EVERY chart; (c) save as a standard asset
(`.inf_mesh` decodes, the derived `.inf_vmesh` decodes, the sidecar hash matches the
bytes); (d) live update -- a store that resolved the mesh BEFORE the edit re-keys after
it, and a pack cooked after the save carries the new bytes; (e) undo the whole journal
back to the baseline byte-for-byte, redo back to the edited state; (f) determinism, the
journal replayed in a fresh SUBPROCESS; (g) the edit-during-Simulate headline, at gate
level; (h) budgets (`LOAD_BUDGET_MS` for opens and saves); (i) cook advisories.

## What it is NOT

There is no blueprint here, and no scripted actor. The Simulate arm needs a world that
*moves* while a save lands in the middle of it, and gravity is the least interesting
thing that does -- which is what you want in a trace whose whole job is to be identical
to a control run.

The prop is small, and that is honest rather than lazy: a hand-modelled prop is a few
dozen triangles, which is **below the cook's `[vgeom] min_triangles`**. The gate asserts
the advisory the cook draws about exactly that, because it is the truth about this whole
class of asset -- see the Phase 23 completion block in `docs/ROADMAP.md`.
